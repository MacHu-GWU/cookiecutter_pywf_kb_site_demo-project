# Strategy: 这个知识库是什么, 写给谁

> 这份文档讲 "这个知识库为什么存在, 写给谁看, 和一般的博客有什么不一样". 写任何一篇之前, 先确认它服务的是这里写的读者.

---

## 1. 它是什么

这个知识库是作者 (一个人或一个团队) 的技术知识库. 每篇文档是作者亲手做过的一件技术事情的完整记录: 为什么要做, 当时的背景, 怎么做, 踩了什么坑, 现在回头看怎么判断.

它是公开的, 但对搜索引擎 `noindex` (见 `sphinx-myst-kb-site` skill). 没有 SEO, 不收费, 不追求流量.

---

## 2. 读者是谁

按重要性排:

1. **未来的作者自己.** 半年后要再做一遍同样的事, 打开这篇就能想起当时为什么这么选, 不用从头查.
2. **AI agent.** 作者的 agent 会通过 `llms.txt` 和每篇的纯文本 (`/p/<doc_id>.md`) 读这里的内容, 拿来回答问题, 写代码, 写新文章. 所以每篇的 `description` 要能让 agent 判断这篇和手上的事有没有关系 (见 [../02-spec/02-metadata.md](../02-spec/02-metadata.md)).
3. **作者把链接发过去的人.** 同事, 朋友, 客户. 他们没有作者的上下文, 只拿到一个链接.

三类读者有一个共同点: **他们都不在作者写这篇的那个现场.** 所以每篇都要把现场交代清楚, 不能只留一份只有当时的作者看得懂的操作清单.

---

## 3. 好文档和坏文档

**坏文档**: 像 AI 生成的摘要. 一上来就是 "第一步, 第二步", 满屏加粗和 ✅, 每一步都对, 但读完不知道为什么要这么做, 这是在哪个项目里, 换个场景还适不适用. 作者以前在 Confluence 上用 AI 直接写的很多页面就是这样.

**好文档**: 有头有尾. 开头交代问题和背景, 中间讲判断和做法 (操作步骤是做法的一部分, 不是全部), 结尾收住: 结论是什么, 适用边界在哪, 什么还没解决. 读者读完能自己做判断, 而不是只能照抄.

写法上的要求见 [../02-spec/04-tone.md](../02-spec/04-tone.md) 和 [../03-workflow/02-writing-process.md](../03-workflow/02-writing-process.md).

---

## 4. 和一般博客的区别

| | 本知识库 | 一般的博客 |
| :--- | :--- | :--- |
| 目录 | 有层级, `docs/source/<分类>/<文档>/` 可以多层 | 平铺 |
| 格式 | `README.md` 为主, 也可以是 `.rst`, `.ipynb` | 只有一种格式 |
| 内容 | 可以很复杂: MyST 指令, 表格, mermaid, 长代码 | 以 H2 / H3 为主的简化博文 |
| 给 AI 的入口 | `llms.txt` 和每篇的 `/p/<doc_id>.md` | 没有 |
| 发布 | Cloudflare Pages, push 到 main 自动部署 | 博客平台上手动发布 |
| 身份 | 随机的 `doc_id`, 文件夹搬家也不变 | URL slug |
| SEO | 不需要, 但有 `created_at` / `updated_at` | 需要 |
| 配图 | 大部分不配, 作者主动要才配 | 大部分都配 |
| 草稿区 | 没有, 写在哪就在哪 | 有 |

**没有草稿区意味着**: 文档一进 main 就会被部署上线. 写到一半的文档也要能通过 `mise run lint-doc`, 不然会卡住整个站点的构建. 所以 `new-post` 建目录时就要求给一个临时的 `description` (见 [../02-spec/01-repository-layout.md](../02-spec/01-repository-layout.md)).
