# Sphinx + MyST Knowledge Base Site

A public, search-engine-hidden documentation site for one person and their AI agents: a folder tree to browse, full-text search, and plain-text access for agents. This file explains what the site does and why it is built this way. For exact code and configuration open `examples/`; when something misbehaves open `references/gotchas.md`.

## The problem it solves

Plain Sphinx ties a page's URL to its folder path, so reorganizing notes breaks every link to them. Markdown is what people and AI write fastest, but plain Markdown has no cross-file references or directives. Free static hosting has no server for search or redirects. AI agents need plain text and an index, not HTML. The site keeps Sphinx's structure and directives, writes in MyST Markdown, and solves the rest with build-time files.

## Features

- Markdown first (MyST), with every Sphinx directive and role; reStructuredText documents and Jupyter notebooks live in the same tree.
- Folder tree of any depth as navigation; table of contents generated from the folders.
- Links that survive moves: inside the site by doc_id, outside by `/p/<doc_id>` (the page) and `/p/<doc_id>.md` (its agent text); every page shows its doc_id and both links as click-to-copy buttons.
- Page navigation by H2 / H3; sphinx-design cards, grids, tabs; mermaid diagrams; SVG files and inline SVG; Python data rendered as tables (sphinx-jinja); part of a source file included by name or by comment markers (literalinclude).
- Type-as-you-search over titles and full text, CJK included, with no server or external database.
- For agents: every document's plain text at one URL, an `llms.txt` index, a `<link rel="alternate">` to the text in every page head.
- Public but `noindex`; deployed on every push to main; one command to deploy locally.

Each feature has a demo document: `examples/docs-source/01-feature-demo/` holds one folder per feature, named after it, and `02-deep-nesting/` shows a four-level tree.

## Terms

- **source**: a document's `README.md`, `README.rst` or `README.ipynb` under `docs/source/`.
- **Sphinx copy**: `_sources/<path>/README.<ext>` in the build, the source as is.
- **agent text**: `p/<doc_id>.md` in the build, the plain text agents read: the Sphinx copy, or for a notebook its compact Markdown copy. "raw" in the page's buttons means this file.
- **permalink**: `/p/<doc_id>`, a redirect to the HTML page.

## Design

From the bottom up; each part builds on the ones before it.

**One document = one folder with a README.** `README.md`, `README.rst` or `README.ipynb`, so GitHub renders every folder too. Metadata lives where each format keeps it: YAML front matter, the top field list, notebook metadata. Sphinx reads all three into `env.metadata` itself.

**Metadata is a contract checked before the build.** `scripts/kb_docs.py`, a strict standard-library parser, finds every document under `<repo root>/docs/source`, lints it and feeds `llms.txt`; `build-doc.sh` runs the lint before Sphinx, so Sphinx never starts on a broken document. The format is a subset on which every YAML parser agrees, so the lint and Sphinx always read the same values.

**Identity is not location.** Every document carries a random 12-letter `doc_id`, fixed for life. The folder tree only serves human browsing; everything that points at a document uses the doc_id. A Sphinx extension registers each doc_id as a label (`` {ref}`<doc_id>` `` links with the title as text), and the build writes Cloudflare Pages `_redirects` rules from `/p/<doc_id>` to the page. Moving a folder changes nothing but the HTML path, and the mapping is regenerated by every build, so there is no redirect service.

**Notebooks without pandoc.** MyST-NB parses notebook Markdown cells as MyST, so notebooks use the same syntax as `.md` pages and the build needs no pandoc. Their committed outputs are shown; the build never runs them.

**Agents read the agent text, never HTML.** After Sphinx, the build writes a compact Markdown copy of each notebook (`scripts/nb_to_md.py`) and copies every document's text to `p/<doc_id>.md` (`scripts/write_permalink_sources.py`). That one URL is what agents get: `llms.txt` lists every document as `[title](<site>/p/<doc_id>.md): description`, and each page's head and raw button link it. Details: `references/gotchas.md#agent-text-permalink`.

**Search is a static index.** Pagefind indexes the built HTML into chunks the browser loads on demand. A small script puts title substring matches first, because Pagefind's ranking and CJK segmentation can bury a title match. Sphinx's own search page remains the fallback.

**One build, two runners.** Two shell scripts (build, deploy) are the only place the commands live. mise runs them locally, and a GitHub Actions workflow without mise runs them in CI. Python is locked by `uv.lock` and the Node CLIs (pagefind, wrangler) by `package-lock.json`, with an exact Node version on both sides, so local and CI builds are identical.

## Decisions and trade-offs

Choices with no right answer, and why this skill picks one side:

- **Two copies: the site's and the skill's.** A site keeps its own `docs/source/`, `.mise/tasks/` and workflow; the skill keeps `examples/`. The site's documents (in the site's language) are what its readers preview; `examples/` keeps the skill self-contained, ready to copy into a new project. The two share one core and one syntax: the same scripts, templates, CSS and JS, and demo documents with the same folders, doc_ids and markup, translated. A site may add features on top (for example, it splits the extension into its Python package and adds an AI Reader link). The price is that a change to the core touches both copies; `scripts/check_example_sync.py` catches the files that drifted.
- **No mise in CI, versions written twice.** mise is for the local machine; CI uses `actions/setup-*`, because installing mise and every tool it manages costs each run more than writing the Python and Node versions in two places, each marked "Must match". No `.tool-versions` file to share them either.
- **mise `[env]` is the source of truth for the site's two values, `KB_DOMAIN` and `KB_SUBDOMAIN`.** The scripts derive the rest (site URL `https://<KB_SUBDOMAIN>.<KB_DOMAIN>`, Pages project name `KB_SUBDOMAIN`); `conf.py` has no default, so a build without them stops instead of writing permalinks to a wrong site. CI reads them as GitHub Actions variables, which `mise run setup-cloudflare-secrets` copies from `mise.toml`.
- **doc_id: 12 letters, no digits or symbols.** Double-click selects it whole, YAML never reads it as a number or a date, and it is a valid Sphinx label. Labels compare case-insensitively, so the space is 26^12, still beyond any collision; the lint checks anyway.
- **Strict front matter, not full YAML.** Authors lose YAML's freedom; in exchange the lint needs no dependency, runs anywhere (an agent, a hook, CI), and nobody ever escapes a quote.
- **HTTP 302 for `/p/<doc_id>`.** Not 301 (cached forever), not a rewrite (relative asset paths break), not a meta refresh (agents do not follow it). `references/gotchas.md#redirect-rules`.
- **One URL for agents.** Prompts and `llms.txt` name only `p/<doc_id>.md`; a second URL is a choice an agent can get wrong.
- **Cloudflare Pages.** Free, private repositories allowed, and, unlike GitHub Pages, it reads `_headers` (`X-Robots-Tag: noindex`, text content types) and `_redirects` from the build.
- **Build from scratch every time.** `rm -rf docs/build` costs seconds and avoids stale toctrees.
- **English UI text on every site.** The buttons show identifiers and URLs, read the same way in any language, and the same template then serves every site. Search's one message picks its language from `<html lang>`.

## Rules

Writing a document:

- Create a folder with a readable slug and an order prefix (`03-some-topic`), never the doc_id; put one `README.<ext>` in it. A parent lists its children with the ```` ```{kb-toctree} ```` directive.
- Metadata: `doc_id` from `scripts/new_doc_id.py`, never changed or reused. `description` is one line without a double quote, written as two sentences: what the document covers, then what kind of document it is ("Covers X, Y and Z. A hands-on demo."). In Markdown front matter `description` is always double-quoted (`description: "..."`); single words such as the doc_id may stay bare, but quote dates and yes/no (`created_at: "2026-11-06"`). Optional `tags: [a, b]`.
- The first heading is the H1 title (the lint rejects a document that starts with `##`).
- Link documents by doc_id, never by path. Give a section you link to a `(<doc_id>-<slug>)=` label; a CJK heading needs one, since `[text](#heading)` works only for ASCII headings.
- In notebooks, write roles and directives in Markdown cells: raw cells are dropped silently. Never commit a converted `README.md` next to `README.ipynb`: the build makes the agent copy itself.
- Run `scripts/lint_docs.py` after writing; the build runs it first anyway.

Changing the site:

- Keep the two shared scripts the single source of the build and deploy commands.
- Change the core in the site and in `examples/` together, then run `scripts/check_example_sync.py`, the example build and the tests (`references/build-and-deploy.md`, section 7).
- Deploying, creating the Pages project and setting GitHub secrets change external services: do them only when the user asks.

## Scripts

Standard library only, no install; any `python3` runs them. Run them from anywhere inside the git repository: their folders default to `<repo root>/docs/source` (`--source_dir`) and `<repo root>/docs/build/html` (`--directory`).

- `scripts/lint_docs.py`: report every metadata, title and layout problem; exit 1 if any.
- `scripts/build_llms_txt.py --site_url <url> [--output <file>]`: write llms.txt (refuses while lint fails).
- `scripts/new_doc_id.py [--count N]`: print fresh doc_ids.
- `scripts/nb_to_md.py [--output_dir docs/build/html/_sources]`: write `<output_dir>/<path>/README.md`, a compact Markdown copy of every `README.ipynb` document (front matter from the notebook metadata, Markdown cells as is, code cells and text outputs fenced, long outputs cut, images and HTML outputs replaced by a note, raw cells dropped). Refuses an output folder inside the source folder.
- `scripts/write_permalink_sources.py [--directory docs/build/html]`: copy each document's agent text to `<directory>/p/<doc_id>.md`; run after `nb_to_md.py`. Fails if a copy is missing.
- `scripts/serve_docs.py --port <port> [--directory docs/build/html]`: serve the built site locally with production's UTF-8 content types.
- `scripts/check_example_sync.py [--repo_root .]`: fail when the site's copy of a shared example file or demo document drifted.
- `scripts/kb_docs.py`: the shared parser (discovery, metadata, titles, lint rules, notebook-to-Markdown, llms.txt rendering). `tests/test_kb_docs.py` covers it.

## Where to look

- `examples/docs-source/`: a complete Sphinx source folder in English that builds as is. Read `conf.py` for every setting with its reason; `_ext/` for the Sphinx extension; `_templates/`, `_static/` and `_extra/` for the furo overrides, the search script and the hosting files; the demo documents for the writing patterns.
- `examples/tooling/`: the two shared scripts, the GitHub Actions workflow, the docs part of `mise.toml`, `package.json`, the secrets setup script.
- `references/build-and-deploy.md`: dependencies, the shared scripts, mise and CI, the one-time setup, and the sync checks.
- `references/access-control.md`: why the site is public by default, and the reserved design (Cloudflare Zero Trust, e-mail one-time PIN, allow-list, service token for agents) for making it private.
- `references/gotchas.md`: every known pitfall as symptom, cause and fix, from documents and rendering up to hosting, local tooling and CI. Open it when a build warns, a link or search result is wrong, or a deploy fails.

To start a new site, copy `examples/docs-source/` to `docs/source/` and `examples/tooling/` into place (the two `.sh` files to `.mise/tasks/`, `deploy-doc.yml` to `.github/workflows/`, `mise.toml` merged into the project's), set the project values in `mise.toml`, the workflow and `conf.py`, then follow `references/build-and-deploy.md`.
